# 常驻 AI 安全工程师

巡御把“常驻安全工程师”实现为一个受约束的闭环，而不是让大模型持有 root shell：

```text
确定性扫描 / 本地变化传感器 / 可信运行时事件
                    ↓
               统一 Signal
                    ↓ 设备 + 稳定目标关联
               Incident 档案
                    ↓ PolicyGrant 允许时
          AI 只读调查 + 严格 JSON 结论
                    ↓
          ResponsePlan（仍未获得权限）
                    ↓ 管理员逐步审查、一次性批准
       强类型 Action → Agent → root Helper
                    ↓
             验证 / 回滚 / 审计
```

## 当前持续观察范围

原生 Agent 会持续维护本地摘要基线；第一次只建立基线，随后才把变化转换为设备身份签名事件：

- `/etc/passwd`、`/etc/group`、`/etc/shadow`、`sudoers` 与 `sudoers.d`；
- `/etc/security`、`sshd_config`、`sshd_config.d` 与 PAM；
- system/user cron、`systemd`、`rc.local`、`profile.d` 与 udev 规则；
- `ld.so.preload`、内核模块加载配置与 sysctl 配置；
- `/etc/docker/daemon.json`。

目录不跟随符号链接，每个文件最多读取 1 MiB，每个目录最多枚举 4096 项。Controller 只接收目标路径、变化类型、前后摘要、发生时间与信任标记，不接收文件正文。

Agent 还维护两个专用运行时传感器：

- 对非 loopback TCP 监听建立最小化基线；只上传端口、地址范围类别和变化类型，具体接口地址以短摘要代替；
- 原生模式由 root Helper 的固定只读接口检查 procfs，只识别“UID 0 从临时可写目录启动”和“运行中的可执行文件已被删除”两类高价值状态；不读取命令行、环境变量、打开文件或进程输出。observer-only 模式只能观察其容器或用户权限实际可见的进程。

监听、进程和单轮事件数量都有明确上限。达到上限时 Agent 会推进一个有摘要的截断基线，并上报 `sensor_health` 容量降级事件；恢复后也会上报恢复信号。这样异常负载不会无限阻塞采集队列，也不会被误解为“没有风险”。

可信 journald 源会记录 SSH 失败与成功登录；成功登录只作为调查证据，绝不授权自动动作。周期扫描继续覆盖账号、SSH、文件权限、端口、防火墙、内核加固、软件包和 Docker Socket 等确定性风险。

这不等于 EDR 的内核级全量遥测。当前进程传感器只处理两类强信号；完整进程行为、内核事件、云审计、应用日志和容器运行时事件仍需要后续接入专用 SignalSource。统一 Signal/Incident 层已经为这些来源保留扩展点。任一来源不可读时，Agent 会记录传感器错误，而不是把“没有读取到”表述为“没有风险”。

原始 SSH 失败记录会保留在有上限的安全事件审计表中；只有同一来源达到用户配置的确定性阈值时，才提升为 Signal/Incident 并可能触发 AI 调查。这避免将公网背景噪声错当成数千个独立案件。

## 授权模式

每台设备的每项能力独立授权：

| 模式 | 自动调用 AI | 自动执行 AI 建议 | 确定性预授权动作 |
|---|---:|---:|---:|
| 仅观察 | 否 | 否 | 否 |
| AI 协助 | 中风险及以上事件 | 否 | 否 |
| 自动低风险处置 | 中风险及以上事件 | 否 | 仅已注册、可逆、受限规则 |
| 增强自动化 | 包含低风险事件 | 否 | 仅该能力允许的已注册规则 |

紧急停止会阻止新的自动决策。observer-only 设备不能把响应计划转换为 Action。第一版唯一经过完整自动执行验证的确定性场景仍是 SSH 暴力尝试的临时 IP 封禁；其他 AI 响应计划都需要逐步批准。

## AI 实际能读取什么

调查 worker 不连接 Agent，也没有通用工具协议。它只在 Controller 数据库上执行八个固定查询：

1. 当前设备的名称、平台、在线状态与观察模式；
2. 当前 Incident 最多 50 条归一化 Signal；
3. 当前设备最多 50 个开放 Finding；
4. 当前设备最多 20 个近期 Action 状态；
5. 当前设备的 PolicyGrant 边界；
6. 最近一份确定性巡检的分数、覆盖状态与检查错误；
7. 当前 Incident 最多 50 条生命周期记录；
8. 当前设备最多 10 个同类历史或活动 Incident。

每种 Signal 另有独立证据字段白名单。新进程事件可以提供 PID、UID、进程名、可执行路径与原因，但命令行和任意 payload 字段不会进入模型上下文；未知传感器默认不透传 payload。证据、路径和错误文本按字段截断，总 JSON 上限为 128 KiB。

模型必须分别输出工作假设、直接观察事实、关键未知、下一步只读检查、结论与置信度。响应上限为 64 KiB，拒绝 Markdown、尾随数据、未知字段、越界置信度、超过 12 条证据项、超过 6 个步骤和未注册动作参数。

## 调查与失败行为

- 只有 `open` Incident 会被后台领取，同一事件通过数据库状态转换避免并发重复调查；
- AI 协助默认忽略低风险噪声，增强模式才处理低风险事件；
- 一轮最多处理 3 个事件，失败后至少 15 分钟再尝试；
- 上游超时、返回无效 JSON 或工具读取失败时，调查记为失败，Incident 回到 `open`，确定性监测不受影响；
- 已完成调查进入 `monitoring`；同一关联键出现新 Signal 时会重新打开，形成连续值守；
- 有 ResponsePlan 时进入 `awaiting_approval`，不会自动变成已批准动作。

## 响应计划如何变成服务器操作

管理员点击某一步时，Controller 会重新读取 Incident、设备与计划，确认设备不是 observer-only，再用该动作类型的固定 schema 重验参数。通过后才原子生成一个绑定计划步骤的 `draft` Action 和 10 分钟有效的一次性批准 nonce。重复点击不能生成第二个动作；只有明确取消的草稿可以重新准备。

批准后仍要经过已有链路：Controller 最终授权、Agent 类型/设备绑定、Helper 本机身份认证、预检、快照、执行、效果验证和可用时的回滚。Action 的签名结果会反向推进 ResponsePlan 与 Incident 状态，避免界面把“模型建议”“已批准”和“已执行”混为一谈。

## 运维建议

- 先在“设置”验证自有 AI 服务，再逐设备开启一个能力的“AI 协助”；
- 观察实际事件量、模型成本和误报后，才考虑增强模式；
- 自动低风险处置只用于已经演练过的确定性规则，并保留带外控制台；
- 定期检查事件时间线、失败调查和 `indeterminate` Action；
- 若怀疑 AI 上游、Controller 或设备被攻陷，立即关闭能力授权、启用紧急停止并轮换凭据。
